# 1. Disaggregated Prefill 개념

## 1-1. 왜 PD 분리를 하는가

일반 vLLM은 하나의 GPU에서 prefill(프롬프트 처리)과 decode(토큰 생성)를 함께 처리한다. 문제는 decode 중에 다른 요청의 prefill이 끼어들면 tail ITL(Inter-Token Latency)이 튀어서 사용자 경험이 나빠진다는 것이다.

Disaggregated prefill은 prefill 전담 인스턴스와 decode 전담 인스턴스를 분리하여, prefill 연산이 decode latency를 방해하지 않게 한다. 핵심은 throughput 개선이 아니라 **tail latency 제어**이다. Chunked prefill로도 비슷한 효과를 낼 수 있지만, 최적 chunk size를 찾기 어렵기 때문에 PD 분리가 더 안정적인 방법이다.

## 1-2. 전체 아키텍처 흐름

vLLM disaggregation은 프록시 서버, 디코드 서버, 프리필 서버를 띄우고, 요청을 프록시 서버로 보내면 prefill 노드가 첫 번째 토큰까지만 생성한 뒤 decode 서버로 첫 번째 토큰까지의 KV 캐시와 첫 번째 토큰을 전달하는 구조입니다

```
클라이언트
    ↓ HTTP 요청
프록시 서버 (:8000)
    ├─→ Prefill 노드 (:8100)  — KV 캐시 생성, 첫 토큰만 생성
    │       ↓ KV Transfer (NCCL or NIXL)
    └─→ Decode 노드 (:8200)  — KV 캐시 수신, 나머지 토큰 생성
              ↓ 스트리밍 응답
         클라이언트
```

상세 흐름:

1. 클라이언트가 프록시에 요청 전송
2. 프록시는 `PROXY_SCRIPT="$REPO_ROOT/benchmarks/disagg_benchmarks/disagg_prefill_proxy_server.py”` 에 구현되어있고 이 python 파일을 키면 프록시 서버가 켜짐
3. 프록시가 prefill 노드로 전달 (이때 `max_tokens=1`로 덮어씀)
4. Prefill 노드가 전체 프롬프트를 처리하여 KV 캐시 생성
5. KV 캐시가 커넥터를 통해 decode 노드로 전송 (NCCL 또는 NIXL)
6. 프록시가 같은 요청을 decode 노드로 전달 (원래 max_tokens 유지)
7. Decode 노드가 수신한 KV 캐시를 사용하여 나머지 토큰 생성 → 스트리밍 응답

> ⚠️ 프록시가 prefill로 보낼 때 `max_tokens=1`로 덮어쓰는데, `min_tokens`는 안 건드린다. 따라서 sweep.py 등에서 `min_tokens`를 설정하면 `min_tokens > max_tokens` 충돌로 400 Bad Request가 발생한다.
> 

## 1-3. 커넥터(Connector) 구조

커넥터는 Prefill과 decode간 KV캐시를 송수신하는 역할을 합니다.(핸드쉐이크, 실제 통신, 버퍼 적재, 요청 ID 관리 등 모든 역할 수행)

decode, prefill 둘다 connector가 존재한다:

- **Scheduler connector**: 스케줄러 프로세스에 위치. KV 캐시 전송 작업을 스케줄링하고, 어떤 요청의 KV를 언제 보낼지 결정
- **Worker connector**: 워커 프로세스에 위치. 실제 GPU 메모리에서 KV 캐시를 읽어서 전송하거나, 수신한 KV를 GPU에 적재

### **사용 가능한 커넥터 종류:**

- `P2pNcclConnector`: NCCL 기반. 공식 예제에서 사용. NCCL이 자동으로 최적 transport 선택 (NVLink → PCIe P2P → SHM → TCP)
- `LMCacheConnectorV1`: LMCache + NIXL 기반. 프로덕션용. YAML config 필요
- `NixlConnector`: vLLM 내장 NIXL 커넥터. UCX transport 사용
- `InstrumentedLMCacheConnector`: LMCacheConnectorV1을 상속하여 KV 전송 시간을 측정하는 래퍼 (우리 커스텀)

### VLLM 공식 커넥터

VLLM에서 지원하는 커넥터 종류로는 LMCacheConnector, P2pNcclConnector **외 7개가 있습니다.** 

이 중 뭘 쓸지가 관건인데 일반적으로 NCCL 과 같은 고속 네트워크 환경에서는 P2pNcclConnector 를 사용합니다. 고속 네트워크가 아니라면, 내부적으로 fallback해서 현재 가장 빠른 통신 방법을 찾아 KV캐시를 전송하기에 이것을 써도 문제는 없습니다.

1. InfiniBand + GPUDirect RDMA
2. RoCE
3. TCP/IP (worst case)

저희환경에서는 여기서 자동으로 TCP를 쓰게 되니 이 커넥터를 써도 통신 자체는 됩니다. 단 여기서 고려지점이 하나 생기는데 이 커넥터는 내부적으로 디코드 노드가 KV캐시를 받았는지 pooling하는 로직이 있습니다. 고대역폭 환경에서는 금방 데이터를 송수신 하니 문제가 없지만 저대역폭 환경에서는 이 pooling이 큰 오버헤드가 됩니다. → 나중에 알고보니 큰 오버헤드는 아님

**단 P2pNcclConnector는 PP를 아직 지원안하는 문제가있음**

따라서 저는 초기에 polling이 없는 LMCacheConnector 를 통해 구현하고자 했으나, 설정이 너무 복잡하고 디버깅할게 상당히 많아 (단일 노드 disaggregation을 가정하고 코드가 만들어짐) 우선 P2pNcclConnector를 통해 구현했습니다. 

### `--kv-transfer-config` JSON으로 커넥터를 설정:

```json
{
  "kv_connector": "P2pNcclConnector",
  "kv_role": "kv_producer",
  "kv_rank": 0,
  "kv_parallel_size": 2,
  "kv_buffer_size": "1e9",
  "kv_port": "14579",
  "kv_connector_extra_config": {
    "proxy_ip": "127.0.0.1",
    "proxy_port": "30001",
    "http_port": "8100",
    "send_type": "PUT_ASYNC"
  }
}
```

- `kv_connector`: 사용할 커넥터 클래스. `P2pNcclConnector` (NCCL 기반, 공식 예제), `LMCacheConnectorV1` (NIXL 기반, 프로덕션), `InstrumentedLMCacheConnector` (측정용 래퍼, 즉 내가 LM캐시 커넥터를 상속받아 만든거라 같은거임)
- `kv_role`: `kv_producer` (prefill) 또는 `kv_consumer` (decode)
- `kv_connector_module_path`: 커스텀 커넥터의 Python 모듈 경로 (InstrumentedLMCacheConnector 사용 시 필수)
- `discard_partial_chunks`: false면 마지막 불완전 청크도 전송 (true면 decode가 재계산)

## 1-4. LookupBuffer & Pipe

vLLM 내부에서 KV 캐시 전송을 추상화하는 두 가지 인터페이스:

- **LookupBuffer**: `insert` (KV 캐시 삽입, non-blocking)와 `drop_select` (조건에 맞는 KV 캐시 반환 후 삭제, blocking). SQL의 INSERT/SELECT+DELETE와 유사.
- **Pipe**: 단방향 FIFO 파이프. `send_tensor`와 `recv_tensor` 지원. 텐서 전송용 기본 인터페이스.

buffer에 insert된 KV 캐시는 drop_select로 꺼낼 때까지 유지된다.

## 1-5. 레이어별 KV 전송

KV 캐시는 한 번에 전송되는 게 아니라 **레이어별로 전송**된다. Llama 8B의 경우 32개 레이어의 KV가 순차적으로 전송됨. `save_kv_layer()`가 레이어마다 호출되고, `wait_for_save()`로 전체 전송 완료를 대기한다.

레이어당 KV 크기 (Llama 8B, fp16): 2(K+V) × 8(heads) × 128(dim) × 2bytes × seq_len = **128KB/token**

- prefill=512: 64MB
- prefill=2048: 256MB

## 1-6. PD 분리에서 Ray를 안 쓰는 이유

PD 분리에서는 Ray를 쓰지 않는다. prefill과 decode가 각각 독립적인 `vllm serve` 인스턴스이고, 서로 전체 모델을 갖고 역할만 다르기 때문이다.

- **멀티노드 TP/PP** (하나의 모델을 여러 GPU에 쪼개 올림): Ray 필수 — 노드 간 워커 연결 + AllReduce 조율
- **PD 분리** (독립 인스턴스, 역할만 다름): Ray 불필요 — KV 전송은 NCCL/NIXL, 요청 라우팅은 HTTP 프록시

논문들(DistServe, Splitwise, Mooncake)에서도 PD 분리에 Ray를 쓰지 않는다.

## 1-7. 프록시 서버의 역할

Prefill decode 인스턴스간 통신은 커넥터를 통해 수행하고, 프록시는 KV캐시 통신은 관여하지 않습니다. 메타데이터 관리등 요청을 조율하는 역할인데 명확한 역할은 아래 3가지 라고 생각합니다.

- 메타데이터 관리 (요청별로 고유한 request_id붙이기)
- 원래 요청의 max_tokens를 기억해두고, prefill한테 보낼 때만 1로 바꿈. decode한테 보낼 때는 원래값 복원 -> 이렇게 해야 prefill이 1 토큰을 생성하게 강제하는 동시에 decode에서 원하는 output_length만큼 만들수 있기 때문입니다.
- Decode가 만든 응답을 스트리밍으로 클라이언트에게 전달합니다 -> 프록시만이 클라이언트가 접근할 수 있는 서버 엔드포인트입니다. 즉 클라이언트 입장에선 서버 내부가 블랙박스입니다. 내부적으로 disaggreagation을 했는지 알 방법이 없습니다.

**공식 프록시** (`disagg_prefill_proxy_server.py`, Quart 기반): P2pNcclConnector용. X-KV-Target 헤더로 KV 소켓 주소를 전달.

**LMCache 프록시** (`disagg_proxy_server.py`, FastAPI 기반): LMCacheConnectorV1용. `/v1/completions`와 `/v1/chat/completions` 두 개의 POST 엔드포인트만 제공.

> ⚠️ LMCache 프록시에는 `/health`, `/v1/models` 엔드포인트가 없다. health check시 주의 필요.

## 2-1. 핵심 질문 (2026-06 재정의)

> ⚠️ **목적 재정의**: 처음에는 "disaggregation 을 써야 하는 이유 찾기", 즉 disaggregation 사용/미사용 비교 + 같은 예산에서 큰 GPU 한 장 vs 작은 GPU 여러 장 비교가 목적이라고 이해했었다. 이는 잘못된 이해였다.
>
> 실제 목적은 **disaggregation 환경 안에서 resource allocation / parallelization strategy 를 최적화하기 위한 환경·워크로드 분석**이다. Disaggregation 사용/미사용 비교는 목적이 아니라 부수적으로만 진행된다.

따라서 우선 실험 해볼 내용은 다음과 같다:

1. **g6.xlarge P1D1 (Config A)** 에서 워크로드별로 **prefill throughput 과 decode throughput 을 각각 정량 측정**했을 때, 둘의 **비율**이 얼마인가? 그 비율이 워크로드(prefill_len / decode_len / rate)에 따라 어떻게 달라지는가?
2. 그 비율에 맞춰 **노드 수 / 병렬화 정도를 늘리면** 전체 throughput 이 균형을 이루는가?
   - 예) throughput 비율이 prefill:decode = 3:1 이면 → prefill 1× g6.xlarge / decode 3× g6.xlarge (decode 인스턴스 증설), 또는 prefill PP1 / decode PP3 을 적용해서 테스트.
   - ⚠️ **단 PP 방식은 이 nccl 브랜치(P2pNcclConnector)에서 불가** — symmetric TP 만 지원하고 PP/asymmetric TP 는 `NotImplementedError`. 따라서 현실적으로는 **decode 노드/인스턴스 수 증설(또는 symmetric TP)** 로 비율을 맞춘다. PP 가 필요하면 LMCache+NIXL 브랜치 사용. (2-2 / 3-5 "PP 실행 불가" 참고)

진행 순서: **① g6.xlarge P1D1 baseline 측정 → ② 워크로드별 throughput 비율 분석 → ③ 비율 기반 GPU 워커 증설 / 병렬화 기법 적용**.

## 노이즈 컨트롤 (실험 공정성 / 재현성)

### Server side (launch_configs.sh)

### 모델 / 정밀도

- **`-dtype half`** — float16 통일 (T4가 bfloat16 미지원 (CC 7.5), cross-config 비교 공정성)
- **`-max-model-len 4096`** — 모든 config 통일, Decode한 토큰씩 생성시 앞에 KV캐시 얼만큼 볼지인데 기본적으로 input + output길이가 이거보다 작으면 에러 발생시킴
- **양자화 미사용** — `-quantization`, `-kv-cache-dtype` 모두 제거 (가중치/KV cache 정밀도 통일, 양자화는 별도 분석 필요)

### 실행 모드 (스케줄러 / 캐시)

- **`-no-enable-prefix-caching`** — KV 캐시 재사용 차단 (매 요청 동일 조건 보장, 캐시 히트가 측정값을 왜곡)
- **`-no-enable-chunked-prefill`** — prefill,deocde 모두  적용 (KV가 한 번에 생성되어 전송 타이밍 단순화), decode에선 켜나 끄나인데 그냥 끔
- **`-enforce-eager`** — CUDA Graph 비활성 (승우님 피드백으로 별로 효과없을것이라 판단)

### 처리량 한계 제거

- **`-gpu-memory-utilization 0.82`** — KV 캐시 용량 결정 (모델 크기에 따라 조정 필요, T4의 OOM 마진 고려한 상한)
- **`-max-num-seqs 512`** — 배치 동시 요청 수 (vLLM 기본값 128이 처리량을 제한시켜 성능을 제한시킬것을 걱정해 열어둠)

### 결정성

- **`VLLM_DISABLE_REQUEST_ID_RANDOMIZATION=1`** — Prefill/Decode 간 request_id 매칭 보장 (intra-GPU는 무관, inter-GPU에서 끄지 않으면 Decode가 KV 받아도 매칭 실패로 연산 불가)
- **`PYTHONHASHSEED=123`** — Python hash seed 양쪽 노드 통일 (dict/set 순회 순서 결정성)

### NCCL 통신 (Config A, cross-node)

- **`NCCL_IB_DISABLE=1`** — InfiniBand 탐색 비활성 (AWS g시리즈에 IB 없음, 켜두면 부팅 시 수 초간 timeout)
- **`NCCL_NET=Socket`** — TCP socket 강제 (transport 선택 노이즈 제거, IB 없는 환경에서 명시)
- **`NCCL_CUMEM_ENABLE=0`** — CUDA cuMem API 비활성 (NCCL 2.18+ 기본 활성화된 cuMem이 P2pNccl 동적 텐서와 충돌 가능성)
- **`NCCL_SOCKET_IFNAME=<auto>`** — 사용할 네트워크 인터페이스 명시 (멀티 NIC 환경에서 인터페이스 선택 노이즈 제거, `ip route`로 자동 추출)

- **`-seed 0`** — 데이터셋/랜덤 토큰 시드 고정
- **`temperature=0`, `top_p=1.0`** (`-extra-body`로 강제) — Greedy decoding (샘플링 노이즈 제거, 모델 `generation_config.json` override)

### 길이 고정

- **`-random-input-len`, `-random-output-len`** — sweep 그리드 값으로 고정
- **`-random-range-ratio 0.0`** — 길이 분산 제거 (정확히 지정된 길이로 생성)
- **`-ignore-eos`** — EOS 토큰 무시 (`max_tokens=decode_len`까지 강제 생성, 조기 종료 방지)
- **`min_tokens` 사용 금지** — 프록시가 prefill에 `max_tokens=1`로 덮어쓸 때 `min_tokens > max_tokens` 충돌 → 400 에러

### 부하 패턴

- **`-request-rate <rate>`** — sweep grid 변수 (실험 변수, control 아님)
- **`-burstiness 1.0`** — Poisson 분포로 도착 간격 생성 (실제 트래픽 시뮬레이션, 1.0이 정확히 Poisson)
- **`-num-prompts 300`** — 통계적 표본 크기 (warmup 10 + 측정 290)

### 측정

- **`-percentile-metrics ttft,tpot,itl,e2el`** — 백분위 측정 대상 지표 선택
- **`-metric-percentiles 50,90,99`** — p50/p90/p99 계산
- **`-save-result`, `-save-detailed`** — 결과 JSON + 요청별 상세 저장 (per-request ttft/tpot/itl 원본값 보존)

### max-model-len 통일의 중요성

max-model-len은 KV 캐시 메모리 예약량을 결정. config마다 다르면 batching 조건이 달라져서 비교 불공정. prefill+decode 합산이 4096을 초과하는 조합은 그리드에서 제거.

### dtype 통일 이유

vLLM에 `--dtype half`를 명시하면, 원본 모델이 BF16이어도 FP16으로 강제 변환하여 로딩한다. T4(CC 7.5)는 BF16 미지원이므로 필수이고, L4/L40S는 BF16을 지원하지만 dtype 효과가 throughput/latency 차이에 섞이는 것을 방지하기 위해 전 config FP16 통일.

# 3. 공식 구현 (P2pNcclConnector)

## 3-1. P2pNcclConnector란

NVIDIA NCCL 라이브러리를 사용하여 GPU 간 KV 캐시를 직접 전송하는 커넥터. vLLM 공식 예제에서 사용한다. 우리도 이걸 사용

**핵심 특징:**

- NCCL이 자동으로 가장 빠른 transport 선택 (NVLink → PCIe P2P → SHM → TCP socket)
- LMCache YAML 설정 불필요
- AWS g시리즈에서는 NVLink/IB 없으므로 same-node=SHM, cross-node=TCP로 자동 fallback
- PP(Pipeline Parallel)는 현재 미지원 → C2 config 불가

**Scheduler / Worker Connector**

공식 예제에서 **P2pNcclConnector가 두 역할을 모두 수행**한다:

- **Scheduler connector**: 스케줄러 프로세스에 위치. KV 캐시 전송 작업을 스케줄링하고, 어떤 요청의 KV를 언제 보낼지 결정
- **Worker connector**: 워커 프로세스에 위치. 실제 GPU 메모리에서 KV 캐시를 읽어서 전송하거나, 수신한 KV를 GPU에 적재

내부적으로 `P2pNcclEngine`의 `send_tensor()`와 `recv_tensor()`가 실제 NCCL 통신을 수행한다.

**NCCL 커넥터 내부 — TCP 모드 물리적 흐름**

**L4 환경(InfiniBand 없음)에서 NCCL TCP 모드 실제 물리적 흐름:**

```
[Prefill GPU memory]
    │ cudaMemcpy
    ▼
[Prefill CPU memory] (NCCL 내부 staging buffer)
    │ TCP send via NIC
    ▼
═══ 네트워크 ═══
    │
    ▼
[Decode CPU memory] (NCCL 내부 staging buffer)  ← Decode CPU 거침
    │ cudaMemcpy (PCIe)
    ▼
[Decode GPU memory] (kv_buffer_size 영역)
     │ 만약 KV_buffer_size 영역을 넘으면`
     ▼ 
Decode CPU pinned memory pool (mem_pool_size_gb = 8GB로 제어)`
     │
     ▼
Decode GPU KV cache (GPU_MEM_UTIL로 제어, 모델이 사용)`
```

**GPU Direct RDMA가 가능한 환경 (H100 + InfiniBand)이면:**

```
Prefill GPU → NIC → 네트워크 → NIC → Decode GPU
                                        ↑
	                               CPU 거치지 않음
```

### kv_connector_extra_config 주요 설정

- `proxy_ip` / `proxy_port`: ZMQ 제어 채널 (프록시와 통신)
- `http_ip` / `http_port`: 이 노드의 HTTP 서버 주소
- `send_type`: `PUT_ASYNC` (비동기 전송)
- `kv_buffer_size`: Consumer 쪽 수신 버퍼 크기 (bytes). g6.xlarge는 RAM 16GB이므로 `2e9` (2GB)
- `mem_pool_size_gb`: pinned host RAM. g6.xlarge는 16GB RAM이므로 8로 제한 (default 32는 OOM)
- `nccl_num_channels`: NCCL 통신 채널 수

`vllm bench serve`을 통해 수집할 수 있는 metric은 다음과 같습니다. (전체 시스템 E2E 관점)

- **TTFT (Time To First Token)**: 50p, 90p, 99p, 평균
- **TPOT (Time Per Output Token)**: 50p, 90p, 99p, 평균
- `benchmark_duration`: 첫 요청 시작부터 모든 응답(생성)이 끝날 때까지 걸린 전체 벤치마크 소요 시간
- `request_throughput`: 전체 초당 처리된 요청 수 (End-to-End 전체 RPS)
- **`total_token_throughput**: (입력 + 출력) 토큰 총합 / benchmark_duration`
- **`output_throughput`** : `최종 응답을 완료한 요청들의 생성 토큰 총합` / `benchmark_duration`

**`output_throughput`** 이 decode의 TPS 고**`total_token_throughput - output_throughput`**하면 Prefill의 TPS아니냐? 아닙니다. **`output_throughput` 와 `total_token_throughput` 의 분모가** 무조건 시스템 전체 소요 시간인 **`benchmark_duration`**으로 묶여 있습니다. 그래서 prefill/decode 중 한곳이 병목이 되고 한곳이 idle이 되어도 전체 소요시간으로 나누기 때문에 각 노드별 실제 RPS를 알 수 없습니다.

### RPS/TPS per-side 측정

vLLM 내부적으로는 prefill/decode 별로 throughput을 분리해서 알려주지 않기에, 각 vLLM 인스턴스의 Prometheus `/metrics` 엔드포인트를 직접 polling하여 노드별 throughput을 측정한다.

**데이터 소스**: 각 vLLM 서버가 노출하는 Prometheus Counter

- `vllm:num_requests_running`: 현재 실행 중(Running)인 요청 개수
- `vllm:num_requests_waiting`: 큐에서 대기 중(Waiting)인 요청 개수
- `vllm:kv_cache_usage_perc`: KV 캐시 메모리 사용량
- `vllm:prompt_tokens_total`: 누적 처리된 프롬프트 토큰 수 (**Prefill 노드만의 순수 TPS** 계산용)
- `vllm:generation_tokens_total`: 누적 생성된 토큰 수 (**Decode 노드만의 순수 TPS** 계산용)
- `vllm:request_success_total`: 처리가 끝난 성공 요청 수 (**각 노드별 순수 RPS** 계산용)

**측정 방법** (`sweep_official.py`의 `MetricsScraper`):

1. sweep 한 point가 도는 동안 매초 Prefill(`http://<prefill>:8100/metrics`)과 Decode(`http://<decode>:8200/metrics`) 양쪽을 polling
2. CSV로 저장 → `{point}.metrics.csv` 시계열
3. 같은 metric 두 시점의 차이 = 그 구간에 한 work. duration으로 나누면 rate
4. active 윈도우 필터: 양쪽 중 하나라도 요청 처리 중일 때만 포함 (첫/끝 idle 구간 제외)

**per-side가 자연스럽게 나오는 이유**:

- Prefill 노드: prompt 처리만 함 → `prompt_tokens_total` 증가, generation은 거의 0 (max_tokens=1)
- Decode 노드: token 생성만 함 → `generation_tokens_total` 증가, prompt 처리는 안 함 (KV transfer로 받으니까)

**결과 필드:**

- `prefill_rps` / `prefill_prompt_tps` ← Prefill `/metrics`에서 차분
- `decode_rps` / `decode_generation_tps` ← Decode `/metrics`에서 차분

**정확도 한계**: 1초 sampling이라 peak는 못 잡고 평균 rate만 나옴. peak 보려면 시계열 CSV를 1초 차분해서 봐야 함.

**정확도 한계 (알아두실 점)**

1. **1초 sampling 간격 한계** — 1초보다 짧은 burst 는 잡지 못함. 매우 빠른 spike 는 평균에 묻힘.
2. **Counter 라 평균 rate 만 나옴** — peak/percentile 은 안 나옴. peak 보려면 시계열 CSV 를 1초 차분해서 봐야 함.
3. **벤치 시작 직후 첫 sample 부정확** — 서버가 막 요청 받기 시작한 시점이라 약간의 warmup 효과 있음. active 필터로 어느 정도 완화됨.

**한 줄 요약**

**각 vLLM 인스턴스의 Prometheus Counter 를 1초마다 polling → 첫·마지막 차분 / 시간 = per-side rate.** 두 노드가 각자 카운트하니까 합치는 게 아니라 그대로 분리해서 보는 것

- vllm bench serve → **client 가 본 end-to-end** (proxy 가 받은 요청 기준)
- 내 /metrics scraper → **각 vLLM 인스턴스 내부 Prometheus counter** 에서 직접 차분 계산 → per-side RPS/TPS

이게 disaggregated setup 에서는 **유일한 방법**입니다. vLLM 가 본질적으로 monolithic 가정으로 만든 거라 P/D 별 metric 은 외부에서 합쳐서 보는 수밖에 없음.

### PYTHONHASHSEED 불일치

**문제**: Prefill/Decode 양쪽 노드에서 같은 request_id에 대해 다른 hash가
나와 KV tensor_id 매칭이 어긋날 수 있음.

**해결**: 양쪽 노드에서 export PYTHONHASHSEED=123 (또는 동일 값)으로

### NCCL timeout / hang

**문제**: 서버 부팅 시 NCCL이 InfiniBand를 탐색하느라 수 초간 멈춤.

**원인**: AWS g시리즈에 IB가 없는데 NCCL이 기본적으로 IB를 탐색.

**해결**: `export NCCL_IB_DISABLE=1`

### mem_pool_size_gb OOM (초기 static OOM)

**문제**: Decode 노드가 부팅 시 `cudaHostAlloc` 실패로 OOM. 즉 `mem_pool_size_gb` 을 원하는 만큼 할당을 못해 나는 에러

**원인**: `mem_pool_size_gb` default가 32GB인데 g6.xlarge는 RAM 16GB. 다른 런타임 프로세스가 몇 GB 이미 사용중.

**해결**: `mem_pool_size_gb: 8`. 나머지는 OS + 런타임용 여유.

### PP 실행 불가

**문제**: configC2 실행 시 즉시 종료.

**원인**: P2pNcclConnector가 Pipeline Parallel 미지원. 코드에 명시적 제한 (`"Currently, only symmetric TP is supported"`).

**해결**: tier1 브랜치(LMCache+NIXL) 사용.

### `max_tokens=1, min_tokens`

**문제**: sweep 실행 시 prefill 노드에서 400 에러.

**원인**: 프록시가 prefill로 보낼 때 `max_tokens=1`로 덮어쓰는데, `min_tokens`는 안 건드림. `min_tokens > max_tokens` 충돌.

**해결**: sweep.py/sweep_official.py에서 `min_tokens` 제거. `ignore_eos=True` + `max_tokens`로 충분.

### cross-node 프록시 하드코딩 문제

**문제**: Config A(cross-node PD)에서 Prefill이 KV 캐시를 보낼 때 자기 자신의 IP로 소켓 연결을 시도하여 무한 대기(Hang).

**원인**: vLLM이 제공하는 공식 HTTP 프록시 스크립트(`disagg_prefill_proxy_server.py`)가 "단일 노드(같은 PC)" 구동만 고려하여 하드코딩 되어 있었음.

- 프록시가 `-kv-host` 인자 단 1개만 입력받음.
- 이를 Prefill 주소와 Decode 주소 양쪽에 동일하게 복사하여 HTTP Header(`request_id`)에 라우팅 주소로 강제 주입함.
- 결과적으로 Prefill 노드(생산자)가 연산 완료 후 KV 캐시를 전송할 때, Decode 노드의 IP가 아닌 **자기 자신의 IP(Prefill IP)로 다이렉트 소켓 연결(`sock.connect()`)을 시도하다가 무한 대기(Hang)** 에 빠짐

**해결**: `--kv-host` 대신 `--prefill-kv-host`와 `--decode-kv-host` 2개로 분리. launch_configs.sh의 `launch_proxy`에서 환경변수 `PREFILL_HOST`, `DECODE_HOST`를 각각 전달.

### NCCL 핸드셰이크 race condition

**문제**: `KeyError: '172.31.x.x:14600'` — decode가 `self.comms`에서 키를 찾지 못함.

**원인**: Prefill이 ZMQ로 NEW 메시지 보낸 뒤 ACK를 기다리지 않고 즉시 PUT 전송.
Decode가 NEW 처리 완료 전에 PUT이 도착 → `self.comms`에 키 없음.

**해결**: `p2p_nccl_engine.py`를 원본 코드로 복구 (커스텀 수정이 race 유발).

**디버깅 노트 — 흔한 오해 배제**:

- 처음엔 "Prefill이 연결하려는 IP와 Decode가 listen하는 IP가 다른 것 아닌가"
하는 IP mismatch 가설을 의심하기 쉽다.
- 하지만 `vllm serve --host 0.0.0.0`로 모든 인터페이스에서 listen하므로
IP 자체로는 mismatch가 발생하지 않는다.
- `launch_configs.sh`의 `http_ip` 환경변수도 명시적으로 설정되어 전달되므로
ZMQ bind 주소도 일치한다.
- 따라서 `KeyError` 증상이 나오면 IP 가설은 빨리 배제하고 핸드셰이크 타이밍을
의심해야 한다. (Prefill 로그에서 `🤝ncclCommInitRank Success`가 Decode 쪽보다
먼저 나오는지, ZMQ NEW → PUT 순서가 올바른지 확인)

### request_id randomization 문제

**문제**: Prefill이 KV를 보내고 Decode가 받지만, Decode scheduler가 `Running:0, Waiting:0` — 요청을 못 인식.

**원인**: vLLM v1 `input_processor.py`의 `assign_request_id()`가 외부 request_id에 random 8-char hex를 추가. Prefill과 Decode가 서로 다른 tensor_id를 보게 됨 → 매칭 실패 → 영원히 hang.

**진단 방법**: `py-spy dump --pid <pid> --locals`로 Prefill/Decode의 request_id 비교.

**해결**: `export VLLM_DISABLE_REQUEST_ID_RANDOMIZATION=1` (Prefill/Decode 양쪽). Proxy가 이미 uuid로 unique request_id를 만들어주므로 충돌 위험 없음.

### KV 캐시 공간 부족 → Decode 처리량 < Prefill 전송 속도 → 버퍼 누적 OOM

**문제**: Llama 3.1 8B + g6.xlarge에서 부하 실험 중 Decode 노드가 OOM으로 죽음.

**원인**:

P2pNcclConnector는 Decode 워커에 KV 캐시를 저장할 공간이 필요한데, 2단계로 구성됨:

1. **1차**: `kv_buffer_size` — GPU VRAM (`GPU_MEM_UTIL`과 별개의 공간에 할당됨)
2. **2차**: `mem_pool_size_gb` — CPU RAM (1차 초과 시 fallback)

prefill에서 계산된 KV는 먼저 decode의 `kv_buffer_size`(GPU VRAM)에 적재되고, Decode 처리 속도보다 KV 유입이 빨라서 `kv_buffer_size`버퍼가 다 차면  `mem_pool_size_gb`(CPU pinned RAM)로 오버플로우됩니다. Decode GPU에 여유가 생기면 CPU에서 다시 GPU로 가져와서 토큰 생성에 사용합니다.

g6.xlarge VRAM 24GB 기준으로 GPU KV cache 공간 계산:

`사용 가능: 24GB × GPU_MEM_UTIL(0.82) = 19.68 GB
   ↓ 모델 가중치 (Llama 8B fp16 ≈ 15GB)
   ↓ CUDA Graph (~3GB)  ※ 실험 당시는 켜져 있었음
   = GPU KV cache 풀: 약 1.46 GB`

vLLM 로그로 확인:

`GPU KV cache size: 11,968 tokens
Maximum concurrency for 4,096 tokens per request: 2.92x`

→ 동시 처리 가능 요청 ≈ **3개**. Decode 배치가 극도로 작아짐.

단순히 적게 처리하는 게 문제가 아니라, **Prefill의 KV 전송 속도 > Decode의 처리량** 이 되면 차이만큼 버퍼(`kv_buffer_size` → `mem_pool_size_gb`)에 계속 쌓이고, 결국 OOM. 즉 **시간이 지날수록 무조건 터지는 구조**.

**시도**: 버퍼를 가능한 상한선까지 키우고 요청 rate도 낮춤

- `mem_pool_size_gb`: 8GB
- `kv_buffer_size`: 1GB
- request rate: 0.5

→ **중간에 여전히 OOM 발생**. 단순히 버퍼를 키워도 누적 속도가 0이 아니면 결국 터짐.

**해결 옵션 분석**:

| 옵션 | 내용 | 평가 |
| --- | --- | --- |
| A. 버퍼 키우고 rate 낮추기 | `kv_buffer_size`, `mem_pool_size_gb` 키우고 요청 rate를 버퍼가 감당 가능한 수준으로 제한 | ❌ 현실 서빙 환경과 맞지 않음. 요청 rate는 고정값이 아니고, 결국 시간이 길어지면 버퍼는 누적되어 OOM |
| B. Decode 처리량 올리기 | 병렬화(DP/PP/TP), 모델 크기 축소, 양자화 등 | ✅ 버퍼에 KV가 쌓이지 않아 안정적 서빙 |

**해결**:

옵션 B 중에서:

- **양자화**: 별도 성능 분석이 필요하여 우선 제외
- **병렬화**: PD 1:1 구조에 여러 병렬화 기법까지 적용하면 경우의 수가 너무 많아짐 → 우선 보류
- **모델 크기 축소**: 채택. Llama 8B → Qwen2.5 3B (가중치 ~6GB → KV cache 공간 충분히 확보). 이후 굳이 낮은 버전을 쓸 이유가 없어 **Qwen3-4B**(가중치 ~8GB)로 재변경 — 2.5-3B 와 크기 비슷하면서 버전만 최신. (2-6 모델 참고)

`launch_configs.sh` 변경 사항 (커밋 `054d1ee70`):

- `MODEL` default: `meta-llama/Llama-3.1-8B-Instruct` → `Qwen/Qwen2.5-3B-Instruct`
- `-quantization awq` 제거 (양자화는 별도 분석)
- `-kv-cache-dtype fp8` 제거
- CUDA Graph도 비활성화 (커밋 `0f7eb19ab`, `-enforce-eager`) — P2pNccl 안정성 우선이며 승우님 피드백에 따르면 P2pNccl 환경에서는 어차피 큰 효과 없음

- (이후 별도 변경) `MODEL` default 를 `Qwen/Qwen2.5-3B-Instruct` 에서 `Qwen/Qwen3-4B` 로, `SERVED_MODEL_NAME` 을 `qwen2.5-3b` 에서 `qwen3-4b` 로 변경

**실험 설계 결정**: 향후 병렬화 기법 적용 시 경우의 수가 폭발하므로, **우선 PD 1:1 구조로 성능 baseline 파악**부터 진행. DP/PP/TP는 baseline 확보 후 별도 실험으로 확장.

> ⚠️ **단, P2pNcclConnector 는 PP(및 asymmetric TP) 미지원** (아래 "PP 실행 불가" 참고 — 소스 `p2p_nccl_connector.py:546` 에서 `NotImplementedError("Currently, only symmetric TP is supported...")` 확인). 따라서 ③단계에서 prefill PP1 / decode PP3 같은 **PP 기반 스케일링은 이 nccl 브랜치에서 불가**하다. PP 가 꼭 필요하면 LMCache+NIXL 브랜치를 쓰고, nccl 브랜치에서는 **decode 노드 수 증설(decode 인스턴스 N개) 또는 symmetric TP** 로 스케일한다.

### CUDA graph OOM(초기 static OOM)

**문제**: 모델(16GB)  + KV + CUDA graph 합계가 GPU VRAM 초과.

**해결**:

# 4.LMCache 구현

## 4-1. 공식 구현과의 차이

| 항목 | 공식 (P2pNccl) | 내 구현 (LMCache+NIXL) |
| --- | --- | --- |
| KV 커넥터 | `P2pNcclConnector` | `LMCacheConnectorV1` (+ `InstrumentedLMCacheConnector`) |
| KV 전송 엔진 | NCCL (자동 transport) | NIXL (LMCache 제공) |
| 설정 방식 | JSON only | JSON + **LMCache YAML** 추가 필요 |
| 통신 경로 설정 | NCCL 자동 | `UCX_TLS` 환경변수로 명시 |
| PP 지원 | ❌ (코드상 `check_tensors_except_dim`에서 shape 불일치 시 NotImplementedError) | 명시적 차단 없음 (미검증, 추후 확장 가능성) |
| CPU 오프로딩 백엔드 | 없음 | `local_cpu` 필수 (LMCache 0.4.5 버그) |
| 프록시 | Quart 기반 (`disagg_prefill_proxy_server.py`) | FastAPI 기반 (`disagg_proxy_server.py`, `/health` 없음) |
| KV 전송 시간 측정 | 커스텀 타이밍 코드 삽입 필요 | ✅ (`instrumented_connector.py`) 내장 |
| 프록시 스크립트 위치 | `benchmarks/disagg_benchmarks/` | `examples/disaggregated/lmcache/` |
| KV 대기 방식 | NCCL busy-polling (CPU spin) | NIXL/UCX event-driven |

**PP 지원 참고**: P2pNcclConnector는 `p2p_nccl_connector.py`의 `check_tensors_except_dim()`에서 "현재 symmetric TP만 지원"이라는 제한이 있어 PP 실행 시 런타임 에러가 발생한다. LMCache는 이런 명시적 차단이 없어 추후 PP 확장 가능성을 고려하여 선택했다. 단, 실제로 PP를 수행해본 것은 아니며 미검증 상태이다.

**KV 대기 방식 차이**: P2pNcclConnector는 NCCL recv 내부에서 busy-polling(CPU spin)으로 KV 도착을 대기한다. 저대역폭(TCP) 환경에서는 전송 시간이 길어져 polling 동안 CPU 자원이 낭비된다. 다만 LLM 서빙에서는 GPU가 병목이고 CPU는 가벼운 역할만 하므로 이 CPU 낭비가 서빙 성능에 직접적 영향을 주지는 않는다. LMCache+NIXL(UCX 기반)은 event-driven 방식이라 busy-polling 없이 CPU를 해제할 수 있다는 구조적 차이가 있다.

## 4-2. LMCache YAML 설정

`launch_configs.sh`에서 각 PD config에 대해 YAML을 자동 생성하여 `LMCACHE_CONFIG_FILE` 환경변수로 전달한다:

```yaml
local_cpu: True              # CPU 백엔드 활성화 (LMCache 0.4.5 호환 필수)
max_local_cpu_size: 3.0       # GB 단위. CPU 오프로딩 버퍼 (실제 사용 안 함)
max_local_disk_size: 0
remote_serde: NULL            # 직렬화 미사용 (NIXL이 직접 전송)
enable_nixl: True
nixl_role: "sender"           # prefill=sender, decode=receiver
nixl_peer_host: "<상대노드IP>" # cross-node면 상대 노드 IP
nixl_peer_port: 55555
nixl_buffer_size: 1073741824  # 1GB (same-node) 또는 268435456 (256MB, cross-node L4)
nixl_buffer_device: "cuda"
nixl_enable_gc: True
```

### 핵심 주의사항

- `max_local_cpu_size` 단위는 **GB** (바이트 아님!). 1048576 넣으면 1 페타바이트 요청 → `cudaHostAlloc failed`
- `local_cpu: False`로 설정하면 `KeyError: 'LocalCPUBackend'` 발생 (LMCache 0.4.5 버그)
- decode 노드의 `nixl_peer_host`에 반드시 **prefill 노드의 실제 IP** 설정. localhost면 KV 미수신 → degraded mode

## 4-3. 통신 경로 (UCX_TLS)

NIXL은 내부적으로 UCX 라이브러리를 사용한다. `UCX_TLS` 환경변수로 통신 경로를 명시적으로 설정해야 한다:

- **Same-node (C1/C2)**: `UCX_TLS=cuda_copy,shm,tcp` — AWS에서 cuda_ipc 차단, shared memory 경유
- **Cross-node (D)**: `UCX_TLS=tcp` — 네트워크 TCP만 사용

NVLink/InfiniBand가 있는 환경이면 `UCX_TLS=cuda_ipc,cuda_copy,rc` 등으로 RDMA 경로를 추가할 수 있다.

## 4-4. max_local_cpu_size vs NIXL 전송 경로

이 두 가지는 **완전히 별개**이다:

| 항목 | 용도 | KV 전송에 영향? | 메모리 위치 |
| --- | --- | --- | --- |
| `--kv-transfer-config` (NIXL) | 노드 간 KV 전송 | **YES** | GPU VRAM |
| `max_local_cpu_size` | GPU↔CPU 오프로딩 버퍼 | **NO** | Host CPU RAM |
| `--no-enable-prefix-caching` | Prefix caching 제어 | **NO** | — |

```
┌─ GPU VRAM (24GB L4) ─┐
│ Model weights: ~16GB │
│ KV cache             │  ← --gpu-memory-utilization 영향
│ NIXL buffer          │
└──────────────────────┘

┌─ Host CPU RAM (별개) ─┐
│ max_local_cpu_size   │  ← GPU VRAM과 무관
└──────────────────────┘
```

## 4-5. InstrumentedLMCacheConnector

`LMCacheConnectorV1`을 상속하여 KV 전송 시간을 측정하는 커스텀 커넥터:

- `save_kv_layer()`: 레이어별 호출 시각 기록
- `wait_for_save()`: 전체 전송 완료 시간 → `kv_transfer.jsonl`에 기록
- rank-0 워커만 로깅 (TP 시 중복 방지)

`launch_configs.sh`에서 `--kv-connector-module-path`로 이 커스텀 커넥터의 Python 모듈 경로를 전달한다.

## 4-7. 트러블슈팅 (LMCache+NIXL)

### 디버깅 로그 설정 (필수)

3장과 동일하게 다음 3가지를 반드시 켜야 한다:

**1. PYTHONFAULTHANDLER=1** — segfault 시 traceback 확인용.

```bash
export PYTHONFAULTHANDLER=1
```

**2. NCCL_DEBUG / NIXL 디버그** — LMCache 브랜치에서는 NIXL이 KV 전송을 담당하므로 UCX 로그도 확인:

```bash
export UCX_LOG_LEVEL=info    # UCX 통신 로그
export LMCACHE_LOG_LEVEL=DEBUG
```

**3. VLLM_LOGGING_LEVEL=DEBUG** — vLLM 내부 동작 상세 로깅.

```bash
export VLLM_LOGGING_LEVEL=DEBUG
```

> ⚠️ Prefill/Decode **양쪽 모두** 설정해야 의미 있다.
> 

### `KeyError: 'LocalCPUBackend'`

**문제**: LMCache 초기화 시 `KeyError: 'LocalCPUBackend'` 발생.

**원인**: `local_cpu: False`면 LMCache 0.4.5에서 백엔드를 생성하지 않는 버그.

**해결**: `local_cpu: True`, `max_local_cpu_size: 1` (또는 3.0). 실제로 CPU 오프로딩을 쓰진 않지만 백엔드 생성을 위해 필요.

### `cudaHostAlloc failed: 2`

**문제**: 부팅 시 `cudaHostAlloc failed: out of memory`.

**원인**: `max_local_cpu_size` 단위가 **GB**인데 큰 숫자를 넣음. 1048576 = 1 페타바이트 요청.

**해결**: `max_local_cpu_size: 3.0` (3GB).

### TTFT 100초+ (KV 미수신, degraded mode)

**문제**: Decode가 KV를 못 받아서 prefill부터 재계산 (degraded mode). TTFT가 100초 이상.

**원인**: decode 노드의 `nixl_peer_host`가 `localhost`로 설정되어 있음. 자기 자신에게 KV를 요청하는 꾸로.

**진단**: 로그에서 `degraded mode` 또는 `recompute` 키워드 확인.

**해결**: `PREFILL_HOST` 환경변수를 필수화하고, launch_configs.sh에서 decode의 `nixl_peer_host`에 자동 설정되도록 수정.

### CUDA graph OOM(초기 OOM)

**문제**: 모델(16GB) + NIXL 버퍼 + KV + CUDA graph 합계가 GPU VRAM 초과.

**해결**: `gpu-memory-utilization: 0.85`로 설정. cross-node L4에서는 `nixl_buffer_size: 268435456` (256MB)로 축소.

### health check 무한 대기

**문제**: sweep.py의 health check가 영원히 통과 못함.

**원인**: LMCache 프록시(FastAPI 기반)에 `/health`, `/v1/models` 엔드포인트가 없음.

**해결**: sweep.py의 health check를 `POST /v1/completions`로 변경. 404/405도 "서버 살아있음"으로 인정.

### 400 Bad Request (prefill) — 공통

**문제**: sweep 실행 시 prefill 노드에서 400 에러.

**원인**: 프록시가 prefill로 보낼 때 `max_tokens=1`로 덮어쓰는데, `min_tokens`는 안 건드림. `min_tokens > max_tokens` 충돌.

**해결**: sweep.py에서 `min_tokens` 제거. `ignore_eos=True` + `max_tokens`로 충분.

### KV 캐시 버퍼 OOM (Decode 병목)

**문제**: 부하 중 Decode가 OOM으로 좽음.

**원인**: Llama 8B fp16 가중치 ~15GB + CUDA graph ~3GB + 버퍼 = KV 캐시에 ~1.5GB만 남음. 동시 ~3개 요청만 처리 가능.

**시도**: AWQ INT4 양자화 + FP8 KV cache → 가중치 15GB→4.5GB. 하지만 decode에서 KV를 받는 건 하는데 연산을 못하는 현상 지속.

**최종 방향**: 3B 모델(가중치 ~6GB)로 전환하여 KV 캐시 여유 확보.

### CUDA 환경 — FlashInfer JIT 컴파일 실패 (공통)

**문제**: DLAMI PyTorch 2.11+는 CUDA가 번들 경로에 있어서 FlashInfer가 `lib64/`를 못 찾음 → `cannot find -lcudart`.

**해결**: setup.sh에서 `lib→lib64` 심링크 + `CUDA_HOME` 설정 + `python3.12-dev` 설치.

### T4 bfloat16 크래시 (공통)

**문제**: T4는 CC 7.5라서 bfloat16 미지원.

**해결**: `--dtype half` 통일.

### ifstat / dcgm-exporter 미설치 (공통)

**문제**: Ubuntu 24.04 DLAMI에 기본 미설치.

**해결**: `sudo apt-get install -y ifstat`. 없어도 실험 결과에 영향 없음.

### degraded mode (recompute) fallback

### 3-3 Prometheus 측정 — "per-side가 자연스럽게 나오는 이유" 보강

당신이 적음:

> Prefill 노드: prompt 처리만 함 → prompt_tokens_total 증가, generation은 거의 0 (max_tokens=1)

**왜 max_tokens=1인지** 안 적혀있어서 나중에 의문 생김. 한 줄 추가:

### 트러블슈팅 #7 (request_id randomization) — 진단 방법이 너무 짧음

> **진단 방법**: py-spy dump --pid <pid> --locals로 Prefill/Decode의 request_id 비교.
> 

py-spy 설치, pid 찾기 방법까지 풀어주면 좋음:

`# Prefill engine 프로세스 찾기

# py-spy 설치 (uv pip install py-spy)
py-spy dump --pid <pid> --locals > prefill_dump.txt
# locals에서 request_id 또는 tensor_id 검색
grep -i "request_id\|tensor_id" prefill_dump.txt`
