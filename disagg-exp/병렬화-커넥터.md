## 0. 핵심 용어 — 커넥터 ≠ 트랜스포트

헷갈리면 안 되는 두 레이어:

| | 정체 | 결정하는 것 | 예시 |
|---|---|---|---|
| **커넥터 (Connector)** | vLLM 쪽 플러그인 (`KVConnectorBase_V1` 상속). **무엇을/언제 옮길지 + producer↔consumer 레이아웃 매핑(TP/PP 재배치) + request_id 매칭 + 스케줄링** | **capability (PP/비대칭TP 되냐 안 되냐)** | `P2pNcclConnector`, `LMCacheConnectorV1`, `NixlConnector` |
| **트랜스포트 (Transport)** | 바이트를 실제로 옮기는 배관 | **속도/경로** | NCCL, UCX/NIXL, TCP socket, RDMA, SHM, PCIe P2P |

**중요한 오해 정정**: "커넥터가 다르면 트랜스포트도 다르니 capability 도 같이 따라가는 거 아니냐"
→ **아니다.** PP·비대칭 TP 지원 여부는 **트랜스포트(배관)가 아니라 커넥터(로직)** 문제다.
두 커넥터가 **AWS 에서 둘 다 결국 TCP 로 떨어져도(같은 배관)**, 한쪽은 PP 되고 한쪽은 안 된다.
"layer 별 KV 를 맞는 PP rank 로 라우팅하는 로직"을 커넥터가 가졌느냐의 문제이기 때문.
→ **트랜스포트가 같아도 커넥터 로직이 다르면 capability 가 다르다.**

커넥터↔트랜스포트 결합도 (대체로 묶여 있긴 함):
- `P2pNcclConnector` → 트랜스포트 = NCCL (auto: NVLink→PCIe P2P→SHM→TCP)
- `NixlConnector` / LMCache(NIXL) → 트랜스포트 = NIXL/UCX (cuda_ipc/shm/tcp/rdma, `UCX_TLS` 로 제어)

## 2. "decode 4D 를 어떻게 쪼개나" — 병렬화 3분류

1P4D 에서 4D(decode 쪽)를 스케일하는 방식은 성격이 다른 3가지:

| 방식 | 정체 | KV 전송 관점 | 노드 |
|---|---|---|---|
| **DP** (복제) | full model decode 인스턴스 **N개**, 라우터가 분배 | 1P → N개 독립 consumer (xPyD). **KV 레이아웃 변환 불필요** | same/다른 노드 무관 |
| **TP** (1인스턴스 분할) | decode **1인스턴스**를 N GPU 에 head 분할 | prefill TP ≠ decode TP 면 **비대칭 TP** → head 재매핑 필요 | 보통 same node (cross-node TP 는 대역폭 때문에 비권장) |
| **PP** (1인스턴스 파이프라인) | decode **1인스턴스**, layer 를 stage 로 분할 | **layer 별 KV 를 맞는 PP rank 로 라우팅** 필요 (제일 어려움) | same 또는 cross node |

- **DP** = "인스턴스 개수" 문제 → 커넥터 입장에서 제일 쉬움 (라우팅).
- **TP** = head 차원 재배치.
- **PP** = layer→rank 라우팅 → 제일 까다로움.
- **혼합** (예: intra-node TP2 × inter-node PP2) = TP 재배치 + PP 라우팅 **둘 다** 필요.

## 4. 같은 노드 vs 다른 노드 — capability gate 아님 (transport + Ray 문제)

- **모든 커넥터가 same/cross node 둘 다 transport 로 처리**한다. capability 를 가르지 않는다.
  - P2pNccl = NCCL (same: SHM/PCIe, cross: TCP)
  - LMCache/NIXL = UCX (same: cuda_ipc/shm, cross: tcp/rdma; `UCX_TLS` 로 명시)
- **실무 함정 2가지:**
  1. **AWS g-시리즈는 NVLink·RDMA 없음** → cross-node = TCP(느림), same-node 멀티GPU(g6.12xlarge) = SHM/PCIe(역시 NVLink 없음). 즉 어느 쪽이든 고속 인터커넥트 없음.
  2. **인스턴스 하나를 노드에 걸쳐 TP/PP 로 펼치면 → 그 인스턴스 내부 분산에 Ray 필요** (커넥터와 별개).
     - 노션 1-6 "PD 분리엔 Ray 불필요" 는 *각 인스턴스가 단일 노드*일 때 얘기.
     - **단일 인스턴스가 노드를 걸치는 순간(예: inter-node PP2) Ray 필요**해짐.
     - 참고: [`vllm/config/parallel.py:111`](../vllm/config/parallel.py#L111) `pipeline_parallel_size`,
       분산 backend 관련 설정도 parallel.py 에 있음.

## 5. 사용자 시나리오별 결론 (1P4D)

| 시나리오 | 분류 | 가능 커넥터 | 비고 |
|---|---|---|---|
| (1) g6.12xlarge 1대에 4D — **DP4** | DP 복제(same node) | 전부 ✅ | **1P4D fan-out 라우터 필요**(아래) |
| (1') g6.12xlarge 1대에 4D — **TP4** | 1인스턴스 분할 | 대칭이면 전부 / 비대칭이면 NIXL✅·LMCache△ | L4 NVLink 없어 PCIe/SHM |
| (1'') g6.12xlarge 1대에 4D — **PP4** | 1인스턴스 파이프라인 | **LMCacheMP △ 만 후보**, 나머지 ❌ | |
| (2) **다른 노드 4개 — DP4** | DP 복제(cross node) | 전부 ✅ | transport 만 TCP |
| (3) **intra TP2 + inter PP2** | TP+PP 혼합, 멀티노드 단일 인스턴스 | **LMCacheMP △ 만 후보** | PP 들어감 + **Ray 필요** + 노드당 2GPU 인스턴스 필요 |

### ⚠️ DP 의 실무 병목 — proxy/router
- DP(복제)는 커넥터 capability 로는 다 되지만, **공식 proxy `disagg_prefill_proxy_server.py` 는 1P1D 단일 타겟**이다 (노션 1-7, 3-2 참고: `--prefill-url`/`--decode-url` 각 1개).
- 1P4D-DP 는 **decode 4개로 fan-out 하는 라우터가 따로 필요** → 이게 커넥터보다 먼저 막히는 실무 이슈. (xPyD 예제 proxy 또는 커스텀 라우터 조사 필요 → TODO)

## 6. "코드 파일 있음 ≠ 됨" — 검증 방법 (△ 를 확정으로 바꾸는 법)

`pp_size` 코드가 있다 = "통합 레이어가 PP-aware 하게 **설계됨**"까지만 보장.
실제 KV 재배치/라우팅 본체는 **설치된 `lmcache` 패키지**에 있고 vLLM 쪽은 얇은 어댑터.
"1P4D PP 가 **실제로 돈다**" 는 런타임 검증으로만 확정:

1. **버전 확인**: `python -c "import lmcache; print(lmcache.__version__)"`
2. **모듈 존재**: `python -c "import lmcache.v1.multiprocess"` (LMCacheMP 전제 조건)
3. **패키지 소스/문서**: site-packages 의 `lmcache/v1/multiprocess/` 에서 PP 재배치 로직 + 릴리스 노트 확인
4. **실제 PP=2 소규모 테스트**: degraded mode(recompute) 로그 없이 KV 전송되고 출력 정상인지.
   - 진단 키워드: `degraded mode`, `recompute`, KeyError(tensor_id), hang
   - `--decode-metrics-url` 로 decode 가 실제 generation 하는지(`generation_tokens_total` 증가) 확인

> .venv/bin/python -c "import lmcache; print(lmcache.__version__)"
> .venv/bin/python -c "import lmcache.v1.multiprocess; print('mp OK')"
> ```
> `mp OK` 안 나오면 → `lmcache` 를 v1.multiprocess 포함 버전으로 업그레이드 필요(핀 상향).

**결론(잠정)**: PP/TP+PP 를 하려면 ① lmcache 를 `v1.multiprocess` 있는 버전으로 올리고
② 커넥터를 `InstrumentedLMCacheConnector`(=LMCacheConnectorV1) → `LMCacheMPConnector` 로 교체해야
한다. 둘 다 AWS 인스턴스에서 검증 필요.
